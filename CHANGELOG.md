# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.2.4] - Unreleased

0.2.4 makes PrismML's **Bonsai 2 27B** (released 2026-09-17) a first-class model and closes a third production-readiness audit of the whole workspace. The 27B is a hybrid `qwen35` model — 48 Gated-DeltaNet layers and 16 gated full-attention layers, with Hadamard-rotated weights — stored in new quantization formats (`PTQ1_0`, `PQ2_0`, group-64 `Q2_0`). Everything needed to run it is new in this release: formats, kernels, model, tokenizer, chat template, reasoning and tool calls, vision, server and CLI, on CPU and on Metal. The file-format and model-support details are in [`docs/models.md`](docs/models.md).

The audit's fixes include several that change what a file means on disk or what tokens a prompt produces. They are listed first so that nothing surprises an upgrade.

### Read before upgrading

- **K-quant GGUFs: the on-disk meaning changed — re-export your files.** Q2_K / Q3_K / Q4_K / Q5_K / Q6_K dequantisation and quantisation were rewritten byte-exact against ggml (core-gguf-K0). Every K-quant file previously written by `oxibonsai quantize` or `oxibonsai-model`'s `export` used a self-consistent but ggml-**incompatible** layout and is now read differently; re-export it. Conversely, third-party llama.cpp K-quant GGUFs, which previously loaded as garbage, now load correctly for the first time. `Q4_0` files stay interoperable; only the encoder's fidelity changes: it now uses ggml's `d = max / -8`, so nibble 0 is reachable (the old `max_abs / 7` mapping used only 15 of 16 levels; core-gguf-Q40), which changes the quantised bytes it writes.
- **K-quant inference on Metal and CUDA was wrong before this release.** The Metal and CUDA K-quant GEMV kernels shared the stale pre-rewrite block layout and are fixed. Measured relative error of the old kernels against the correct dequantisation: Q3_K 0.93, Q4_K 0.65, Q5_K 0.64, Q6_K 0.0119, Q2_K 0.0013. Anyone who ran K-quant inference on Metal got wrong logits.
- **GGUF files written by OxiBonsai follow ggml's metadata and alignment rules; whether llama.cpp reads one depends on its tensor types.** `general.quantization_version` is written as `u32 2` and the architecture keys as `<arch>.*` instead of `llm.*` (core-gguf-02); tensor offsets are alignment-padded (core-gguf-10). Mainline-typed tensors (Q4_0, the K-quants, F16/F32) are readable by llama.cpp. The default `oxibonsai convert --quant tq2_0_g128` (what `scripts/download_ternary.sh` runs) writes OxiBonsai's runtime-native `qs`-first group-128 ternary layout under ggml id 42 (`general.file_type` 41, `oxibonsai.quant_format = "TQ2_0_G128"`); the runtime executes it on every tier, but neither mainline llama.cpp (which reads id 42 as the 18-byte group-64 `Q2_0`) nor the PrismML llama.cpp fork (which expects `d` first) reads it. `--quant pq2_0` writes the same ternary data as PrismML `PQ2_0` (id 142, `d` first), which the PrismML fork reads and mainline does not; 0.2.4 cannot run a `qwen3` model stored that way (it has no `PQ2_0` LM-head wrapper). Files written by earlier versions — `llm.*` keys, the string version tag `"TQ2_0_G128"`, back-to-back offsets — still load.
- **The same prompt can produce different tokens.**
  - Greedy argmax breaks ties toward the **first** index on every route (RT-22); the GPU argmax kernels now agree with the CPU loop (perf-11).
  - Models that declare `rope.scaling.type = yarn` (Bonsai-8B: factor 4, original context 16 384) now decode with YaRN applied at **all** positions (mscale 1.1386), exactly like llama.cpp. Greedy output of such models differs from 0.2.3 and earlier; the new output is byte-identical to the PrismML llama.cpp fork. `--rope-scaling off` (or `[model].rope_scaling = "off"`) reproduces the old behaviour; `on` on a model without scaling keys is refused naming `<arch>.rope.scaling.*`.
  - Seeded sampled realisations change for `top_k > 0` requests (canonical survivor order: raw logit descending, an exact tie to the lower index). CPU == Metal identity and greedy output are unchanged, and `top_k == 0` realisations are unchanged.
  - There is no hidden repetition penalty any more: `oxibonsai serve` no longer applies `repetition_penalty = 1.1`, and the defaults of `SamplingConfig` / `SamplerBuilder` are `1.0`, so greedy means greedy on every entry point.
  - The ternary GEMM accumulation order changed (K-18: register-blocked, Rayon-parallel). Batched CPU prefill is cos ≥ 0.999-equal to the old loop, not bit-equal. Metal ternary prefills of 8–63 rows use the new tiled kernel (cos ≥ 0.999 against the row-wise one, not bit-identical).
- **The built-in model configurations were wrong and now equal the real files (M-34).** `Qwen3Config::bonsai_1_7b()` matched no shipped file: block count 16 → 28, embedding length 1536 → 2048, FFN 4096 → 6144, heads 12 → 16, KV heads 2 → 8, vocabulary 151 936 → 151 669, context 65 536 → 32 768. `bonsai_8b()` gained FFN 14 336 → 12 288, vocabulary 151 936 → 151 669 and its real `rope.scaling = yarn(factor 4.0, original_context_length 16 384)`, which was previously parsed and silently ignored (so the shipped 8B produced wrong output beyond 16 384 tokens). `ModelVariant::from_config` now detects the 1.7B from (28 layers, hidden 2048) instead of (16, 1536).
- **Safer network defaults (sec-15).** Both server binaries bind `127.0.0.1` by default. `/admin/*` answers 403 until an admin token is configured; both binaries read `OXIBONSAI_ADMIN_TOKEN`, then `OXI_ADMIN_TOKEN`. The bundled chat UI is off unless `--enable-ui` is passed. Metrics label unmatched routes as `route="other"` instead of the raw path (an unbounded memory-growth vector), and `/metrics/serve` obeys `observability.metrics_enabled`.
- **GPU selection is explicit.** A default-on `metal` Cargo feature for macOS was prototyped and reverted: it moved the default decode tier and broke default-feature builds. Build with `--features metal` (or `native-cuda`) for a GPU build and choose the executor at run time with `--backend auto|cpu|metal` (default `auto`; `metal` never silently falls back to the CPU).
- **The real MSRV is 1.89** (deps-02). `rust-version = "1.86"` was false: the dependency graph does not resolve below 1.89. Raising it changes no resolved version.
- **The Pure-Rust default-feature guarantee is enforced.** `aws-lc-sys` (BoringSSL C and assembly) left the default dependency graph (deps-01): downloads use the COOLJAPAN `oxihttp` client. `scripts/check_pure_rust.sh` fails the gate if `cc`, `cmake` or `bindgen` is reachable from the resolved default-feature dependency graph (it prints the reverse-dependency path, and heuristically scans dependency `build.rs` files for compiler shell-outs), and `deny.toml` bans the C-backed crates. `core-foundation-sys` (the platform binding to Apple's CoreFoundation framework, through `chrono`; no C is compiled) is the only `-sys` node in the default graph and is allowed.
- **CI is a repository script.** `.github/workflows/ci.yml.disabled` is gone; `scripts/ci.sh` is the gate, `scripts/release-gate.sh` layers the real-model legs on top, and `scripts/publish.sh` has no `--skip-ci`. The old workflow is preserved for reference in `docs/ci-reference.yml`. `./scripts/ci.sh` includes a `RUSTDOCFLAGS="-D warnings"` docs stage and a coverage-baseline stage that runs the tests under `cargo llvm-cov nextest` (one process per test, run with every route to a real model file closed, so its real-model tests skip and their evidence is the nextest stages and the release gate, with a capability report of its own; there is no coverage threshold yet). The `wasm-tokenizer` stage also checks `oxibonsai-runtime` for `wasm32` with warnings denied.
- **x86_64 AVX2 activations now round like NEON (K-M3).** On AVX2+FMA hosts `silu_simd`, `swiglu_simd` and `softmax_simd` use the same Cephes-style polynomial `exp` as the NEON path (within 1 ulp of the correctly rounded value, clamped at ±88.376) and run the 1–7 element tail through the identical vector core, so a value is bit-identical wherever it lands in a buffer (the AVX2 body used to compute `x · (1/(1+e))` with libm `exp` while the tail computed `x / (1+e)`, a 1-ulp split by position). Versus 0.2.3, SiLU/SwiGLU outputs move by up to 4 ulp, `silu` is absolute-error-only below −88.376 (and `silu(−∞)` is `−∞`, not NaN), a softmax logit more than ≈87.68 below its row maximum is exactly `+0.0` instead of a subnormal, and the softmax denominator adds the tail as its own group. The scalar tails of `rms_norm_simd`, `rope_apply_simd` and `norms::rms_norm_gated_simd` now use the vector body's multiply association, a last-bit change only for lengths that are not a multiple of the lane width (8 on AVX2; 4 for NEON `rms_norm_simd`).
- **An FP8 GEMV through a CPU-tier `KernelDispatcher` no longer reaches a GPU kernel.** The FP8 GEMV dispatch tried Metal/CUDA regardless of tier, so on a GPU host an engine loaded with `--backend cpu` (a model loaded under `Backend::Cpu`) silently ran FP8 GEMVs on the GPU. GPU kernels are now attempted only on `KernelTier::Gpu`; a GPU miss falls back to the best CPU SIMD tier (K-17), `KernelTier::Gpu` FP8 dequant/GEMM run that SIMD tier instead of the scalar reference, and `Fp8Kernel::name_fp8()` reports `fp8_gpu` on a Gpu tier built with an FP8 GPU kernel (it said `fp8_reference`). CPU-tier FP8 results on GPU hosts therefore change from the GPU kernel's rounding to the tier's own CPU kernel's; GPU-less hosts are unchanged. A model's FP8 linears keep the dispatcher they were loaded with, so a library engine built with a CPU-tier dispatcher around a model loaded outside `Backend::Cpu` still reaches the GPU (see Known limitations).

These compile in-workspace but break out-of-repo consumers.

- `server::image_support::ImageSupport`'s `NotHybrid` / `BackendUnavailable` variants became `Refused { code, message }` (`from_refusal` is new); `InferenceEngine::multimodal_executor()` and `prefills_images()` are the public pre-encode questions.
- `StreamingDecoder::finish()` (`oxibonsai-tokenizer`) is now infallible; `finish_strict()` is the opt-in error form. `EmbeddingTable`'s `Index<Range<usize>>` impl and `dense_view()` were removed; `EmbeddingResponse` gained `dimension` and `normalized`.

### Added

**Bonsai 2 27B (`qwen35` hybrid)**
- **Formats and loading.** ggml type ids `PQ2_0` (142, 34 B / 128 weights, `d` first) and `PTQ1_0` (143, 28 B / 128, `d` last), mainline group-64 `Q2_0` (id 42, 18 B / 64), with a resolver that settles the three incompatible layouts that ship under id 42 from the offset table and a structural sniff of real block bytes — never a guess (`OXI_FORCE_Q2_LAYOUT` overrides it; [`docs/models.md`](docs/models.md)). `prism.hadamard.*` metadata is parsed and validated the way llama.cpp validates it; the `qwen35` configuration (`HybridConfig`) and `ModelVariant`s for the 27B family are new. `oxibonsai pull` downloads and verifies all six 27B language files, the mmproj and `Bonsai-8B`.
- **Kernels.** Dequantisation and GEMV/GEMM for `PQ2_0`, group-64 `Q2_0` and `PTQ1_0` (scalar reference, NEON, AVX2; GEMM is register-blocked and Rayon-parallel), a lossless `PTQ1_0` → `PQ2_0` transcode (`--ptq1-transcode`), the blockwise 1024-point Hadamard transform with fused sign flips, the Gated-DeltaNet recurrence, causal depthwise conv1d, gated RMSNorm, L2-norm, the sigmoid attention gate, partial RoPE (64 of 256 dimensions) with M-RoPE sections, and head-dimension-256 GQA attention. CUDA ports of these kernels exist but are compile-only (see Known limitations).
- **Model.** A hybrid transformer block (linear or full attention per layer), a recurrent-state cache beside the KV cache (conv windows and the 128 x 128 `S` matrices per linear layer), chunked Gated-DeltaNet prefill (`--prefill-chunk`, default 512), and a RAM-derived context plan: the KV cache is sparse `f16` at 65 536 B per position, the default window is 8192 positions, and the CLI refuses a window above the model's declared context or the RAM-derived bound.
- **Metal hybrid runner.** With `--backend auto` (the default) on a Metal host the 27B runs on the Metal hybrid runner; weights are mapped in place (runner build 0.1–0.3 s). Measured on an M3 with 24 GB as ranges because the host was under background load (load average 6–22): decode 6.9–8.4 tok/s (CPU path 1.0–1.3 tok/s), first token 0.57 s on a 5-token prompt, and the runner's batched prefill runs at 4.1–6.3x its own decode rate at 512 tokens (it was equal to the decode rate before); greedy ids equal the CPU path and the reference implementation on three prompts per format. At the default 8192-position window the runner allocates 1.02 GiB at load, 0.50 GiB of it `f16` KV (785 MiB at 4096 positions). `--backend cpu` keeps the CPU tier; `--backend metal` refuses with `HYBRID_GPU_BACKEND_UNSUPPORTED` naming the constraint when the build or host cannot serve it.
- **Tokenizer and chat contract.** The native tokenizer reads the GGUF vocabulary with the `qwen35` pre-tokenizer pattern (compiled with `fancy-regex`, backtrack-capped; a deliberate, recorded deviation from a hand-written splitter, and its `Llama3` pattern is an approximation of the GPT-2 one). The GGUF's own `tokenizer.chat_template` is rendered by a real Jinja subset (a ChatML/Qwen3 fallback covers files that ship none, including tools and `enable_thinking`). `<think>` blocks are split into `reasoning_content`; `enable_thinking` and `reasoning_effort` (`low` / `medium` / `xhigh`) are honoured; `<tool_call><function=...>` XML tool calls are parsed and streamed. Every control and user-defined special token (the 27B's `248044..=248076` block, including the vision markers) is neutralised in user content by vocabulary class.
- **Vision (`--mmproj`, `--image`, `image_url` content parts).** The `clip` / `qwen3vl_merger` projector loads from the mmproj GGUF; PNG and JPEG are decoded in Pure Rust; image rows are prefilled by the model with three-axis M-RoPE positions. On a Metal host with `--backend auto` the 27B **stays on the Metal hybrid runner**: the vision tower runs on the GPU with the file's exact `Q8_0` weights (0.87 GiB resident against 1.71 GiB for the CPU tower) and the runner prefills the image rows. Measured on an M3: the reference 256 x 192 prompt end to end through `oxibonsai run` takes 14 s on Metal against 78 s with `--backend cpu`; the tower encodes 256 x 192 in 0.12–0.13 s and 768 x 768 in 2.6–2.7 s (CPU tower: 1.8–6 s and 23–30 s); greedy ids equal the CPU path and the reference on both formats. Both reference prompts are reproduced token for token on the CPU path. A server without a projector answers an image request with `400 vision_unavailable`; a dense model answers `400 NOT_A_HYBRID_MODEL`.
- **Embeddings.** Hybrid models serve `/v1/embeddings` (5120-dimensional, mean-pooled, L2-normalised, final-normed hidden state in the model's own un-rotated basis; the embedder runs on the CPU model whatever `--backend` says).
- **Sampling defaults** come from the GGUF's `general.sampling.*` keys (temperature 1.0, top-p 0.95, top-k 20 for Bonsai 2); end of turn is `<|im_end|>` (248046), and a requested window is refused above the model's declared 262 144 tokens or the RAM-derived bound.

**CLI**
- New subcommands `pull` (verified model downloads; `--band pq2|ptq1`, `--vision`, `--force`, `--out`) and `build-info` (enabled features, compiled-in kernel tiers, the tier detected at run time and why, git commit). `info` and `validate` print the kernel tier once, report the hybrid memory plan, and `info --mmproj` reports what each vision tower would keep resident.
- New flags on `run` / `chat` / `serve`: `--backend`, `--rope-scaling`, `--ctx` (alias of `--max-seq-len`), `--prefill-chunk`, `--ptq1-transcode`, `--think` / `--no-think`, `--reasoning-effort`, `--tools`, `--mmproj`, `--image` (not on `serve`), `--image-max-tokens`, `--allow-image-url-fetch`, `--image-url-timeout-ms`, `--image-url-allow-host`, `--allow-vocab-mismatch`; on `run` / `chat`: `--chat`, `--show-reasoning` / `--hide-reasoning`, `--top-k`, `--min-p`, `--repetition-penalty`, `--frequency-penalty`, `--presence-penalty`, `--grammar`, `--stop`, `--seed`, `--no-stream`; on `serve`: `--cuda-device`, `--rate-limit-rpm` / `--rate-limit-burst`, `--cors-origin` / `--cors-allow-credentials`, `--max-body-bytes`, `--max-output-tokens`, `--bearer-token-file`, `--enable-ui`, `--media-path`, `--embedding-backend model|none|tfidf` with `--embedding-corpus`; `convert --allow-unmapped` and `convert --quant pq2_0|ptq1_0|q2_0_g64`; `eval --tokenizer-backend`. See [`docs/CLI.md`](docs/CLI.md).
- `--seed` on `run` / `chat` / `benchmark` layers flag > `[sampling].seed` (TOML, underscores allowed: `seed = 1_000`) > 42; `oxibonsai serve` honours `[sampling].seed` (`OXIBONSAI_SEED` env > TOML > a pseudo-random default). `run` / `chat` clamp the generation budget to what `--ctx` has left and print a "context window full" notice (exit 0) instead of crashing; a prompt that alone exceeds `--ctx` is still a hard error naming both numbers.
- **Remote image references, opt-in.** With `--allow-image-url-fetch` (or `OXI_ALLOW_IMAGE_URL_FETCH=1`) `run` / `chat --image https://...` and a `serve` request's `http(s)` `image_url` are fetched by a Pure-Rust fetcher (the `oxihttp` client already in the binary; no new C, no proxy) under an address policy, then decoded exactly like a data URI (the same `prompt_tokens`). One `GET` per image — no body, cookies, credentials or retries, `User-Agent: oxibonsai/<version>` — at most 3 redirects followed by the fetcher itself (each hop vetted again, `https` → `http` refused), a `200` answer of at most 32 MiB (a larger `Content-Length` refused before the body, a missing or lying one cut off past the cap), and one deadline per image over resolution, connect, TLS, head and body: `--image-url-timeout-ms` (flag > `OXI_IMAGE_URL_TIMEOUT_MS` > 10 000; `0` or a non-number is a start-up error). `--image-url-allow-host <host[:port]>` (repeatable; added to the comma-separated `OXI_IMAGE_URL_ALLOW_HOSTS`) exempts exactly the named hosts from the public-address rule, for intranet image stores; an allowlist (the flag or the variable) or an `--image-url-timeout-ms` without the opt-in is a start-up error (`OXI_IMAGE_URL_TIMEOUT_MS` is read only once opted in). The three settings are read only by a command given `--mmproj` (and checked there before the model loads): a text-only `run`, `chat` or `serve` never consults `OXI_ALLOW_IMAGE_URL_FETCH`, `OXI_IMAGE_URL_TIMEOUT_MS` or `OXI_IMAGE_URL_ALLOW_HOSTS`, so a stale value in the shell or `.env` cannot stop it. New error codes, both `400` with `error.param = messages`: `image_url_refused` (the address policy refused the URL or a redirect hop) and `image_url_fetch_failed` (the step that failed: resolve, connect, connect/TLS, response, status N, redirect, body, or "timed out after N ms"); an oversized body is `image_too_large`, and without the opt-in a remote reference is still `image_url_fetch_disabled` with nothing opened. `serve`'s start-up log and `info --mmproj` report whether remote images are fetched, the deadline and the allowlist; a `504 request_timeout` caught during a fetch names the new `image_fetch` phase. The library seam is `oxibonsai_model::vision::RemoteImageFetcher` (`ImageSourcePolicy::remote` replaces the unreleased `allow_remote_fetch` field; `ImageSourcePolicy::with_remote_fetcher`), with the pure policy in `oxibonsai_model::vision::remote` for fetchers of one's own, and `VisionService::with_fetch_observer` / `ImageFetchObserver` for a server that tracks one request's fetches (`CurrentFetch` lets a fetcher see the request it fetches for: drop the fetch once the request is abandoned, or report that it is at capacity, which surfaces as `MultimodalError::FetchOverloaded`, code `image_fetch_overloaded`).
- `oxibonsai serve` resolves the tokenizer and chat template once at startup; the standalone `oxibonsai-serve` binary consumes `config.ui.enabled` and `config.limits.max_output_tokens` (new `OXIBONSAI_ENABLE_UI`, `OXIBONSAI_MAX_OUTPUT_TOKENS`) and hard-errors, like the CLI (TOK-08), when an explicit tokenizer does not fit the model's vocabulary. A GGUF's `general.sampling.min_p` is applied as every engine-pool replica's baseline (`EnginePool::set_min_p_all`; the standalone binary reads no GGUF sampling defaults).

**Server and OpenAI-compatible API**
- `/v1/chat/completions` and `/v1/chat/completions/extended` accept `image_url` content parts (streamed or not), `reasoning_content`, `tools` with `stream: true` (each completed call is one `delta.tool_calls` entry; the final `finish_reason` is `"tool_calls"`), per-request `min_p` and `stream_options.include_usage`; `seed` + `logprobs` is accepted on the base chat endpoint. An unclosed or malformed tool-call block at the end of a response is returned as content with the natural `finish_reason` (it used to keep only the preamble and force `length`) on both endpoints, streamed or not. The `/extended` non-stream response carries `tool_calls` at the choice level, while the base endpoint and both stream paths use `message.tool_calls` / `delta.tool_calls`.
- `/v1/completions` really streams (`stream: true`, single prompt or batch: one SSE stream, `choices[0].index` = the prompt's index, one `[DONE]`; batches are capped at 8 prompts) and accepts `seed` together with `logprobs`; a batch seeds prompt `i` with `seed + i`. It is `#[serde(deny_unknown_fields)]`: a typo'd field is a 400 `unknown_parameter` naming the field, as are a non-empty `suffix`, `n` or `best_of` other than 1, a non-empty `logit_bias`, `top_k > 1 000 000` and `min_p` outside `[0, 1]`. Chat requests stay open-vocabulary.
- `/readyz` (a model is loaded and the engine pool can serve; `engine_slot_available` says whether a replica is idle right now) is distinct from `/health` (liveness only): a server whose every replica is busy is ready-but-saturated and answers `200`, and `503 not_ready` is for a server that cannot serve at all. With no tokenizer attached a text prompt is a 400 `tokenizer_required` unless `RouterOptions::with_prompt_start_token` supplies a start token (the hardcoded Qwen3 id is gone). The KV-window budget applies on every endpoint: a prompt at or above the window, or prompt + `max_tokens` above it, is refused up front; a request that outlasts the timeout answers 504 `request_timeout` naming the phase (`preparing`, `image_fetch`, `vision_encode`, `waiting_for_engine`, `prefill`, `decode`). `/rag/query` routes through `Retriever::retrieve_with_top_k`, so it applies the retriever's configured `rerank` flag (scores and order can change for pipelines with rerank enabled) and answers 400 to a degenerate, fully-out-of-vocabulary query instead of 200.
- `/v1/embeddings` answers `501` with the real refusal reason (`error.code`, `error.message`) and `type: not_implemented_error`; `--embedding-backend tfidf` is served through `RouterOptions::with_embeddings_registry` with every guard (bearer, rate limit, body limit, admission) unchanged. `/v1/models` lists the file stem when `general.name` is a placeholder such as `Hf` (`/admin` shows both). Typed refusals precede any image decode (`NOT_A_HYBRID_MODEL` as 400 with `error.param = messages`; `BACKEND_UNAVAILABLE` is reserved: no shipped executor raises it, since both hybrid executors prefill image rows), the decoded-pixel budget refuses `image_too_large` from the header, and the vision-marker vocabulary check runs at `--mmproj` load. `--media-path` (flag > `OXI_MEDIA_PATH` > default) scopes `file://` image references.

**Kernels, performance and the dense Metal path**
- **Opt-in INT8 dot-product tier.** `OXIBONSAI_KERNEL_TIER` (`int8-scalar`, `neon-int8`, `neon-dot`, `neon-i8mm`, `avx512-vnni`) reaches the native `TQ2_0_g128` / `Q1_0_g128` CPU tiers at all seven kernel entry points and the PrismML `PQ2_0` / group-64 `Q2_0` paths. The activation is quantised to INT8 once per call (one scale per weight block) and every block accumulates exactly in `i32` (`SDOT` on `neon-dot`; `SMMLA` for batched GEMM plus `SDOT` for GEMV on `neon-i8mm`; `VPDPBUSD` on `avx512-vnni`). It is lossy and **never selected by default**: unset, the f32 kernels run bit-identically. Measured: minimum cosine against f32 0.999991–0.999993 on real weights, worst end-to-end teacher-forced logit cosine 0.9996 with greedy argmax agreement 27/27 per model, `neon-i8mm` 8.76x CPU decode on Ternary-Bonsai-1.7B (29–36 tok/s through the engine; 6.5 → 39.2 tok/s in the model forward; host load average 15–20), 2.6x on the real 27B at cosine 0.999996 with the same argmax. The GPU tier is never diverted — Metal output is byte-identical with the variable set, proven on the real 1.7B and Bonsai-8B — *as long as the GPU prefill actually runs*: when it declines or fails, the CPU batched prefill (and the batched CPU embedding pass, `forward_hidden`, on any engine) runs on the selected INT8 tier. A tier the CPU cannot run is demoted with a one-time warning; `PTQ1_0` has no INT8 kernel; `avx512-vnni` compiles and passes clippy but has never run on VNNI hardware.
- **Dense Metal prefill is no longer super-linear (M-18, closed).** The row-wise 1-bit Metal GEMM re-read its input once per weight row, so fused prefill cost grew with the batch (Bonsai-8B fused prefill was *slower* than sequential decode: 0.52x at 256 tokens). A simdgroup-tiled Q1 GEMM (`gemm_q1_g128_simdgroup`) and cheaper ternary staging replace it from 8 rows. Measured on an M3, host load average 6.5–22: Bonsai-8B fused prefill is 8.05–8.2x faster per token than sequential decode at 256 tokens (5.6–5.9 ms against 46.2–47.2 ms), a 4096-token prompt takes 27.5–29.4 s against 304–322 s, and the per-token cost grows 1.19–1.23x from 256 to 4096 tokens; Ternary-Bonsai-1.7B: 11.9–12.5x, 7.4–7.6 s against 130–134 s, 1.41–1.43x. (The Bonsai-8B "before" row at 4096 tokens was measured on a 512-token prompt, because the pre-fix 4096-token arm did not finish within 900 s.) `DEFAULT_PREFILL_CHUNK_TOKENS` stays 4096; chunk size is flat within 3–6 %. A bounded command-buffer wait with a typed timeout falls back to the sequential path, and a measured cost-model router (`MetalPrefillPolicy`) diverts a prompt whenever the fused path is predicted slower. The flash-attention prefill kernel is 1.38–1.41x faster per layer and bit-identical.
- **Dense embeddings** use a head-free Metal hidden prefill: 2000 tokens in 3.3 s on a 1.7B and 13 s on the 8B models, pooled cosine ≥ 0.99999998 against the sequential reference (batched CPU: 45–52 s; per-token loop: 352 s). Without Metal, dense embeddings run the batched CPU prefill instead of the per-token loop: 11.4–20.7x faster on the real Ternary-Bonsai-1.7B across 10, 200 and 2000 tokens (load-dependent), bit-identical output. The batched CPU prefill, which generation uses too, splits GEMMs over batch x feature slabs and runs attention row-parallel (12.06x over sequential prefill).
- Per-forward Objective-C autorelease pools on every Metal path (hybrid runner, dense, vision tower): each forward leaked about 1.8 KiB (about 1.8 GB per million tokens on a long-lived server thread; about 21 KiB per embedding request on the dense path). 1550 forwards now change the process footprint by less than 0.25 MiB on every route.
- **Engine-pool sizing.** Replicas buy isolation and latency fairness, not GPU throughput. Real Ternary-Bonsai-1.7B, 8 concurrent greedy requests, M3: pools of 1 / 2 / 3 replicas serve 52.2 / 54.2 / 54.5 tok/s aggregate (median +4.5 % / +5.5 %; a loaded-host re-measurement gives a paired per-round median of 1.038x for 2 and 1.043x for 3), resident weights 457 MB for all three, byte-identical outputs; Bonsai-8B `Q1` replicas 2–3 add no weight memory.
- Sampled top-k decoding on Metal can read back only `k` candidates instead of the full logits row; it is available as an opt-in (`InferenceEngine::set_sampled_topk(SampledTopKConfig::gpu_candidates())`) and its output is byte-identical to the full-row draw, but it is off by default because its selection kernel costs about 25 ms per token at a 151 669-token vocabulary (22 against 57 tok/s on Ternary-Bonsai-1.7B). Default-sampled decode therefore reads the full row, as in 0.2.3, and a real-model test (`real_model_default_sampled_decode_keeps_pace_with_greedy`) holds it to at least 0.6x the greedy rate in one process. `InferenceEngine::set_min_p` / `min_p`.
- Kernel selection is logged once per process per (tier, reason) by `oxibonsai_kernels::dispatch_log`; later identical constructions log at `DEBUG`.

### Fixed

- **Numerics and kernels.** K-quant dequant/quantise (core-gguf-K0), the Q4_0 encoder (core-gguf-Q40), Metal/CUDA K-quant GEMV, greedy tie-breaking (RT-22), the GPU argmax first-index tie-break (perf-11), the out-of-bounds read on a short norm tensor (M-01), and `RopeTable` position bounds (M-27).
- **Kernel determinism and dispatch.** FP8 dispatch moved to `dispatch_fp8.rs` behind a `fp8_gpu_gemv` cfg alias emitted by `build.rs`, classifies the benign no-device case by error variant (`CudaGraphError::DeviceNotFound` / `MetalGraphError::DeviceNotFound`) instead of allocating a message to search, hands the GPU kernels exactly the bytes they read, and refuses weight images their 32-bit indexing cannot address (the sizing is a pure function with its own tests). The AVX2 `exp_avx2_f32x8` / `silu_core_avx2_f32x8` cores are pinned bit-for-bit to a shared scalar Cephes model on each architecture, with an `#[ignore]`d exhaustive sweep of every `f32` in [−87, 87] in-repo. `tests/gemv_no_alloc.rs` warms the K-quant per-thread scratch on every Rayon thread before measuring (a cold worker's one-time 32 KiB growth failed 12 of 40 runs on an 8-core host; no assertion was relaxed). The remote-image tests prefer a `[::1]` second listener, fall back to `127.0.0.2` on the same port on hosts without IPv6 loopback — announced with a `NOTE (capability)` line, with `127.0.0.2` spellings added so the fallback listener stays falsifiable — and capability-skip only when neither binds; any other bind error is a loud panic. clippy 1.99's new lints (`chunks_exact_to_as_chunks`, `needless_late_init`, `manual_slice_fill`, `byte_char_slices`) are clean workspace-wide, with the numeric rewrites checked bit-for-bit against the old loops.
- **Hybrid decode.** A recurrent-state reset seam (RT-28) so a stale `S` matrix can no longer contaminate the next request; speculative decoding and the prefix cache refuse hybrid models instead of rolling a recurrence back (M-35); the prefix cache is off for hybrid models.
- **Server robustness.** Cancellation reaches every generation (SV-09): on `/v1/chat/completions`, `/v1/chat/completions/extended` and `/v1/completions`, streamed or not, a request whose `--request-timeout-ms` expires or whose client disconnects has its generation cancelled at the next step (and a request with several choices or prompts starts none of the rest), so its replica serves the next request instead of decoding to `max_tokens` for nobody; `/extended` and `/v1/completions` now carry the base endpoint's own deadline — `504 request_timeout` with `error.phase` (and `error.generated_tokens` in decode), or the SSE `error` event then `[DONE]` once a stream is open — where they used to get only the admission layer's `408` two seconds later; `max_tokens`, temperature, `top_p` and `n` validate with honest 400s; n-gram speculative decoding could return up to `draft_len` tokens more than `max_tokens` and now stops exactly at the budget; seeded requests carry the engine's min-p (they silently ran with min-p 0).
- **`/rag/query` no longer generates on an async worker.** The handler embedded the query, searched the store, tokenised the prompt and ran the whole generation inline on a tokio worker — seconds to minutes on one worker, probe routes included — could not be dropped while the engine ran, and had no deadline of its own, so a client that left left its replica decoding to `max_tokens` for nobody. Retrieval, prompt assembly and tokenisation now run as one stage on the blocking pool, and the generation goes through the chat routes' non-streamed seam (`run_blocking_generation` with the abandonment guard): a dropped handler — a disconnect, or the admission layer's `408` — cancels it at the next step and frees the replica. A router built with `create_rag_router_with_options(.., RagRouterOptions::default().with_limits(..))` enforces the server's per-request deadline inside `/rag/query` exactly as the chat routes do: an expired deadline cancels the generation and answers `504 request_timeout` with `error.phase` (`preparing`, `waiting_for_engine`, `prefill`, `decode`) and, in decode, `error.generated_tokens`; `oxibonsai serve --rag` hands it `--request-timeout-ms` and the server's metrics. `/rag/index` fits and indexes on the blocking pool too, stops between documents when its client leaves, and replaces the index only once it is complete; the pipeline is shared as an immutable snapshot, so `/rag/stats` and an index swap no longer wait for a search, and a poisoned pipeline lock no longer turns every RAG route into a `500`. A query whose prompt fits one prefill chunk (512 tokens) answers byte for byte what it answered before; a longer prompt is now prefilled in 512-token chunks, as the chat routes' prompts are, and so carries the chat routes' chunked-prefill numerics (on the CPU path, a split that leaves a one-token tail differs from an unchunked prefill by a few f32 ULPs). The runtime's `rag` feature now implies `server` (the RAG routes use its blocking-pool and deadline seams), which also makes `--no-default-features --features rag` build.
- **The probe and metrics routes answer while the server is at its concurrency limit.** In both `oxibonsai serve` and `oxibonsai-serve`, admission wrapped every route, so with the concurrency budget full (`4 x pool` requests in flight: four generations on a one-replica server) `/health`, `/readyz`, `/metrics` — and `GET /v1/models` — answered `503 overloaded_error`. A liveness probe then restarted a server that was merely busy, and the metrics scrape went blind exactly when it mattered. `/health`, `/readyz`, `/metrics` and `/ui/health` (and, on `oxibonsai-serve`, `/metrics/serve` and the `observability.metrics_path` alias) are now answered outside the budget; they still honour the body limit, the rate limiter (which exempts only `/health` and `/metrics`, as before), bearer auth (exemptions unchanged), CORS and the request timeout. `GET /v1/models`, generation, embedding and `/admin/*` routes stay inside the budget and shed with `503` + `Retry-After`; a route added later is inside it unless it is named in `ADMISSION_EXEMPT_PATHS`, and a test enumerates each router's routes to keep it so. `/readyz` answers `200` at the limit — a server whose every slot and replica is busy is ready-but-saturated, and `engine_slot_available: false` in the body says no replica is idle — and `503 not_ready` only for a server that cannot serve at all, never the admission layer's overload error. Both binaries now resolve the model descriptor at start-up, while every replica is idle, so the probe never waits for a replica.
- **The admission timeout's `408` has a stable error code.** Its body carried `error.code: null`; it is now `request_timeout`, the code the handler's own `504` deadline carries (status `408` and `error.type: timeout_error` are unchanged; it names no `error.phase`).
- **`--help` text matches the behaviour.** `serve --pool-size` states the real sizing rule (a Metal tier or a Bonsai 2 model defaults to 1; an explicit size is honoured on the CPU and capped at `OXIBONSAI_METAL_MAX_SESSIONS` on Metal; it no longer claims an unconditional clamp to 1), `serve --rate-limit-burst` names its built-in default (a flat 20, not a multiple of the RPM), and `--tokenizer-backend hf` is described as the opt-in `hf-tokenizer` build feature rather than on by default.
- **GGUF robustness.** The batch and streaming parsers agree on tensors with more than four dimensions (core-gguf-16) and both reject a non-`UINT32` `general.alignment` (core-gguf-15); one shared bounded string reader (core-gguf-20).
- **`oxibonsai convert --quant tq2_0_g128` writes native `TQ2_0_g128` (id 42) again.** During the 0.2.4 cycle, since core-gguf-02, the converter default mapped `tq2_0_g128` to PrismML `PQ2_0` (id 142), which the `qwen3` runtime cannot load (it has no `PQ2_0` LM-head wrapper), so every Ternary-Bonsai GGUF freshly made by `scripts/download_ternary.sh` failed at load. This was an unreleased regression (0.2.3 wrote id 42) and is fixed: `tq2_0_g128` writes id 42 (`general.file_type` 41) and only `--quant pq2_0` writes id 142; `tq2_0_g128_converts_to_native_id_42_and_loads` converts and loads the result. Ternary GGUFs made with a pre-release 0.2.4 build from 2026-09-23 on should be reconverted.
- **CUDA Q4_0 batch prefill: wrong first token.** `gemv_q4_0_pf`, the Q4_0 LM-head GEMV at the end of a CUDA batch prefill, read each block's nibbles even/odd-interleaved instead of ggml's low/high split. On a `native-cuda` build a prompt of more than 16 tokens on a model with a Q4_0 LM head therefore produced wrong last-token logits and a wrong first generated token; the layers and the K/V read-back were correct. In 0.2.3 this path ran only with `OXIBONSAI_FORCE_CUDA_SPLIT_PREFILL=1`; 0.2.4 runs it by default at position 0, with the K/V read back into the host cache, and no longer honours that variable (setting it logs one error and changes nothing). Found and verified on an RTX A4000: 48-token greedy output is now byte-identical to the CPU, and CUDA-P11 passes for Q4_0 and Q8_0.
- **Chunked prefill no longer emits a 2..=16-token final window (F-3).** Both chunk planners — the engine's (`InferenceEngine::set_prefill_chunk_tokens`, used by the server's 512-token deadline windows) and the model's (`BonsaiModel::set_prefill_chunk_tokens`, set by `--prefill-chunk N`, and its default 4096-token plan) — fold a final window of up to 16 tokens into the previous one whenever the chunk is larger than 16 tokens, so a Q1 or ternary prompt on native CUDA is no longer refused with `GPU_FALLBACK_REQUIRES_CACHE_REBUILD` after its device-KV batch chunk. Verified on the CPU (window plans, logits bit-identical to a one-shot prefill for both planners) and on the RTX A4000 (the P14/P15 harness's `chunk=120` arm: a 133-token Bonsai-8B prompt runs as one fused window, cos 1.000000, 8 greedy tokens identical to the sequential path; a caller-cut 13-token window is still refused, see Known limitations).
- **Ternary CUDA decode no longer re-uploads the weight set every token.** The fused ternary decode rebuilt its per-layer Q‖K‖V host concatenation on every token and hashed the buffers' addresses into the CUDA weight-set fingerprint. When the allocator returned new addresses (it does on the streaming worker thread of `run` / `chat` / `serve`), the weight cache treated the model as new: it evicted about 1.85 GB, re-uploaded it and re-captured the CUDA graph, every token. The concatenation is now built once per model (one resident host copy, about 240 MB for the 8B), and the fingerprint hashes buffer lengths and the per-layer weight-handle ids. Ternary-Bonsai-8B on an RTX A4000, a 48-token greedy `run`: 48 evictions → 0, 1.0 → 8.0 tok/s, output unchanged (the fixed build's 256-token `benchmark` gives 10.8 tok/s).
- **CUDA Q1 decode no longer risks reusing a dropped model's weights.** The Q1 weight cache (one uploaded weight set per process) was validated by a fingerprint of host buffer addresses and lengths only (pre-existing), so a Q1 model of the same shape loaded after another was dropped could be decoded with the old model's device weights if the allocator handed it back every freed address. It now applies the ternary path's rule: the per-layer weight-handle ids, which are unique to each loaded model, plus buffer lengths and the addresses of the model-owned buffers. On an RTX A4000, a new hardware test that writes a second same-depth Q1 weight set (synthetic weights) into the first set's host memory gets the second set's own output, where the old fingerprint returned the first set's output exactly; the F-M1 model-swap test still passes. A reload of two real Q1 model files in one process was not run.
- **`scripts/check_cuda.sh` passes under a real `nvcc`.** Its host stubs (`uint3`, `threadIdx` and the other launch built-ins, `rsqrt`, `__popc`, the integer `min` / `max`, the execution-space macros) collided with the CUDA headers, so the authoritative `nvcc` tier failed all 31 kernel sources on any host with the toolkit; they are now compiled only outside `__CUDACC__`. The two archived `Q1_0_g128` kernel sources include `<cuda_fp16.h>`, and the approximate tier skips its `__expf` shim on glibc, so it also parses on Linux. With CUDA 12.0 (2026-10-07): 31/31 pass, `CUDA_SYNTAX_RESULT=nvcc-ok` (on the tree before the `gemv_q4_0_pf` fix below changed one kernel source; the fixed kernel was compiled by NVRTC and run on that GPU, but has not had an `nvcc` pass).
- **`--backend cpu` no longer runs Q4_0 / Q8_0 / K-quant GEMVs on CUDA (F-2b).** On a `native-cuda` build the Q4_0, Q8_0 and K-quant linear layers called their CUDA GEMV whenever a CUDA device opened, so a model loaded with `--backend cpu` (`Backend::Cpu`) decoded on the GPU while the CLI reported a CPU kernel tier: 6107 CUDA kernel launches for an 8-token `run` of the Q4_0, Q8_0 and Q4_K fixtures on the RTX A4000. These layers now decide at construction whether they may use the GPU, as FP8 layers do: a layer constructed under `CpuOnlyBackendScope` (which `Backend::Cpu` enters around model construction) never tries a CUDA GEMV, whichever thread later runs it, and a K-quant layer constructed there runs on a CPU-tier dispatcher that never probes the GPU. The engine's CUDA warm-up is skipped for `Backend::Cpu`; it only spent CPU time at load there. `--backend auto` is unchanged. On a CUDA host `--backend cpu` results therefore come from the CPU kernels instead of the CUDA ones. Verified on the RTX A4000 with nsys: an 8-token greedy `run` under `--backend cpu` now makes no CUDA call at all (no kernel launch, no CUDA API call) with the Q4_0, Q8_0 and Q4_K fixtures (6107 kernel launches each before), as with Bonsai-8B and the FP8 fixture, and a 26-token prompt makes none with Q4_0 and Q8_0 (10244 before); `--backend auto` launches as many kernels as before (5364 / 5364 / 6107 / 136803, and 8245 for the 26-token prompt) and logs the same lines; the generated text is unchanged under both.
- Off-macOS builds of the facade with `--features metal` no longer warn about unused `blocks_as_bytes` helpers (the `cfg` was narrowed).

### Security

- **`RUSTSEC-2023-0071` (the `rsa` crate's "Marvin Attack" timing side-channel) is an accepted vulnerability, not an unmaintained-crate ignore.** It entered the dependency graph with the `aws-lc-sys` removal (oxihttp → oxitls → `oxitls-rustcrypto-provider`, where `rsa` is a mandatory dependency with no avoidance knob; no safe upgrade exists upstream). The acceptance rationale is checkable: this workspace uses the stack only as a TLS **client** verifying server certificates (a public-key operation), TLS 1.3 key exchange is ECDHE, and no client certificate is configured anywhere. **The acceptance is invalidated the moment mTLS with an RSA client certificate is added through this stack**; `deny.toml` carries a standalone, greppable "INVALIDATED IF" line for it. Revisit by 2027-03-31.
- The `MPL-2.0` and `0BSD` licence allowances were dropped from `deny.toml` (nothing in the graph carries them). The dev-only `criterion` / `alloca` / `cc` exception is **load-bearing**: `required-features = ["bench"]` stops the bench sources compiling, but Cargo still builds every dev-dependency when any test target is selected, so `cargo test --no-run` still compiles `cc`, and the `aarch64-unknown-linux-gnu` cross-target lint still fails on `cc-rs`. The `objc` → `objc2` port is deferred: `metal` 0.33 exposes no safe `error()` / `gpu_start_time()` / `gpu_end_time()` accessor and itself depends on the old `objc` crate, so `objc` stays in the tree regardless — it is hygiene, not Pure-Rust compliance.
- **Remote images are off by default, and the opt-in is fenced.** Without `--allow-image-url-fetch` / `OXI_ALLOW_IMAGE_URL_FETCH=1` an `http(s)` image reference is `400 image_url_fetch_disabled` before any connection or name lookup. With it, the fetcher dials only public unicast addresses: every address a host resolves to must be public or the whole fetch is refused (no "next record"), refused classes being loopback, private, carrier-grade NAT, link-local (cloud metadata at `169.254.169.254`), this-network, documentation, benchmarking, protocol-assignment, 6to4-relay, multicast, reserved and broadcast IPv4, and `::`, `::1`, IPv4-mapped and IPv4-compatible IPv6 (whatever they embed), NAT64, discard-only, Teredo, 6to4, unique-local, link-local, site-local, multicast and everything outside `2000::/3`; IP literals are classified in every spelling the client or `inet_aton` accepts (`2130706433`, `0x7f.1`, `0177.0.0.1`, `[::ffff:127.0.0.1]`, a trailing dot; a zone id is refused) and `localhost` / `*.localhost` are refused by name. Names are vetted inside the HTTP client's resolver hook, so the addresses vetted are the addresses dialled (DNS rebinding); every redirect hop is vetted again; no proxy is consulted (`HTTP_PROXY` and friends are ignored); URLs with credentials are refused and masked in messages, which never name a resolved address; logs record scheme, host, port, status, bytes and milliseconds, never the path or query. The operator's allowlist (`--image-url-allow-host`, `OXI_IMAGE_URL_ALLOW_HOSTS`) exempts the named hosts from the address classes and the `localhost` rule, and from nothing else. What the opt-in exposes: any public `http(s)` server a client names (the fetch is a `GET` from the server's address), plus the allowlisted hosts; keep it off on a public endpoint unless clients need it. A fetch whose request is over (client gone, deadline expired) is dropped at once, connection closed, and the process runs at most 8 fetches plus 8 waiting (a wait for a transfer slot counts toward the per-image deadline) — beyond that a request gets `503 image_fetch_overloaded` with `Retry-After` before anything is opened; fetches are not counted by `--max-concurrent-requests`, so set the rate limit when remote fetching is on. `file://` references stay inside `--media-path` (symlink escapes are refused); the decoded-pixel budget is enforced from the image header.

The macOS release host has no `nvcc`, so its gate still checks CUDA kernel syntax approximately under the `--accept-approximate-cuda-syntax` waiver. The `cuda` (scirs2) feature is a CPU fallback, not a GPU build. `multi_gpu.rs` is a rayon simulation (its types are named `SimulatedDeviceMesh` / `SimulatedCollectives`), `distributed.rs` is in-memory only, `PagedKvCache` is experimental, and `DeviceInfo::memory_bytes` is a labelled placeholder.
- **CUDA, as measured on an RTX A4000.** Q4_0 / Q8_0 / K-quant / FP8 decode uploads each weight matrix on every GEMV call (6–10 GB/s host-to-device during decode): correct but PCIe-bound, and it can be slower than the AVX-512 CPU path (a Q8_0 Ternary-Bonsai-1.7B fixture decodes at 3.8–4.0 tok/s on CUDA against 6.2 tok/s on the CPU). The Q1 batch prefill runs at 0.6–0.8x the speed of the per-token CUDA path on that GPU (68–74 ms against 45 ms per prompt token on Bonsai-8B); the ternary batch prefill is 1.4x faster than per-token. A K-quant or FP8 model's CUDA warm-up runs a 17-token sequential prefill (3–10 s at load). Ternary-Bonsai-8B holds 5739 MiB of VRAM during `run` for a 2081 MiB file. `oxibonsai quantize` keeps `output.weight` and `token_embd.weight` in F32, so its Q4_0 / Q8_0 / K-quant / FP8 output never reaches the CUDA LM-head branches, which are selected by the LM-head type (the hardware run used fixtures with a quantized LM head, built by `oxibonsai-model/examples/quantize_full_head.rs`); `quantize` also cannot read `PQ2_0`, `PTQ1_0` or group-64 `Q2_0` sources.
- **A library engine's CPU-tier dispatcher does not reach the FP8, Q4_0, Q8_0 or K-quant linears.** These layers decide at load whether they may use the GPU: an FP8 layer keeps the `KernelDispatcher::auto_detect()` that `BonsaiModel::from_gguf*` built for it, and a Q4_0 / Q8_0 / K-quant layer records whether a `CpuOnlyBackendScope` was active. On a GPU build an engine assembled with `KernelDispatcher::with_tier(Reference | Avx2 | …)` around a model loaded outside that scope therefore still runs those GEMVs on the GPU (observed on CUDA on the RTX A4000). `--backend cpu` / `Backend::Cpu` loads the model under the scope, so on CUDA it runs none of them on the GPU (see Fixed). On a Metal build the Q4_0 / Q8_0 layers still try the Metal GEMV under `Backend::Cpu` (from reading the code; not run on Metal hardware).
- **CUDA prefill can still refuse a short window from a library caller.** With a Q1 or ternary model on native CUDA, the batch prefill leaves the K/V device-resident and the per-token path (windows of up to 16 tokens) reads the host KV cache, so a following window of 2..=16 tokens is refused with `GPU_FALLBACK_REQUIRES_CACHE_REBUILD`. In 0.2.4 both chunk planners fold such a tail into the previous window when the chunk is larger than 16 tokens (see Fixed), so the server and the CLI's default plan do not emit one. Still refused: `--prefill-chunk 2` to `16` (every window takes the per-token path, so the second one is refused), and a library caller that drives `forward_prefill` with its own windows. The fold was verified on the CPU (window plans, bit-identical logits) and awaits a CUDA re-run of `cuda_q1_chunked_prefill_short_tail_chunk_characterize_cache_rebuild_refusal`: its planned 133-token prompt at chunk 120 must pass parity against the sequential path, and its caller-cut 120 + 13 windows must still be refused; the test fails on purpose, after printing a parity verdict, if that caller-cut refusal is ever gone.
- Real-model gates cover the two 27B variants present on the reference host (`PQ2_0`, `PTQ1_0`); the other four 27B language files are covered by header, loader and fixture tests. The eval logit tasks have never been run against a real model.
- `OXIBONSAI_METAL_MAX_SESSIONS` (default 4) is reported by `oxibonsai info` but **not enforced** when a session opens (a Metal vision tower is a second session; each pool replica adds one). The dense Metal prefill guard has caveats: its budget clock starts before staging, so a cold first call can time out and send the next prompts down the sequential route; the verify path has no router; the probe counter is per model with no decay; a forced route persists until the mapping epoch changes. Memory outside every budget: the serve embedder's CPU engine, replica-against-replica overlap, and the vision tower unless the window plan carries its term. The dense-engine rewind log is partial (speculative and prefix-cache drivers move the KV cursor directly).
- **Metal waits on the Bonsai 2 27B are unbounded.** The Metal hybrid runner and the Metal vision tower wait for each command buffer without a time limit (a failed buffer is a typed error, a stalled one is not); only the dense batched prefill has the bounded wait and the cost-model router. A stalled GPU therefore holds the engine replica (and the tower) while the client receives its `504`, and a Metal engine has no CPU-tower fallback (it never loads the CPU tower).
- **What an abandoned request still finishes.** A request abandoned (client gone, or its deadline expired) while its images are being encoded still finishes encoding every image it carried before the tower is free for the next request — up to 16 images, seconds each on Metal, tens of seconds each on the CPU tower; only the generation and the remote fetches stop at once. A streamed request's SSE deadline is counted from the moment the stream opens, so its total wall time can reach the time spent before the stream opened plus `--request-timeout-ms` (at most twice the setting).
- **Remote image fetching, once opted in, makes the server an HTTP client for every API caller.** The address policy keeps it off loopback, private and special-purpose ranges, but: an allowlisted host (`--image-url-allow-host`) is readable at any path by any client, and redirects to it are followed; error messages distinguish an unresolvable name, a non-public one, a failed connection, an HTTP status and a redirect's target, so names and ports can be probed from the server's network position; "public" is decided by address class only, so egress filtering belongs on the firewall; a fetched image is bounded by its own 32 MiB cap (16 per request), not by `--max-body-bytes`; `https` to an IPv6 literal is not supported. The fetcher is compiled into every native build and is inert without the opt-in. See the Security notes in [`docs/DEPLOYMENT.md`](docs/DEPLOYMENT.md).
- **No real-weight Bonsai-Image evidence in the release gate.** The `image-parity` capability (Bonsai-Image text-to-image on real weights) is not required by any gate flag and self-skips on a host without the image weights; the image pipeline's parity is covered by its own tests and examples, not by the gate.
- Divergences from the reference vision implementation: the `--image-max-tokens` default is 1024 (the reference server's own limit is 4096); an over-budget elongated image is refused; `Picture N:` labels appear only with add-vision-id; the PNG decoder is stricter; "never upscales" means no upscaling to reach the budget; two error codes differ in casing. The CPU vision tower takes 23–30 s for a 768 x 768 image (a 15 s target was waived; the Metal tower is the fast path). `oxibonsai info` prints the KV-only 65 536 bytes per position.
- RAG and eval: the RAG vector store is a brute-force `entries x dim` scan (50 000 entries of 384 dimensions is about 73 MiB and 19 million multiply-adds per query); an HNSW index behind an `ann` feature is a deliberately deferred, project-sized item. BLEU's `ExpDecay` smoothing is not verified against NIST/Chen & Cherry's method 3 and chrF's effective-order vectors are hand-derived from the F-beta formula rather than sacreBLEU reference values (both need a networked golden-vector pass).
- The release checklist includes the opt-in M-08 20 000-token YaRN long-context run (`OXIBONSAI_M08_RUN_LONG=1`) and `scripts/release-gate.sh` end to end plus the `wasm32` check (see [`docs/DEPLOYMENT.md`](docs/DEPLOYMENT.md)).
- Deferred design items: chunked UT-transform Gated-DeltaNet prefill, a recurrent-state ring buffer for prefix caching, the MTP/NextN draft head, Hadamard KV-cache rotation, video input (`<|video_pad|>`, temporal slice 2), and `qwen35moe` / `qwen3next`. See `TODO.md`.
